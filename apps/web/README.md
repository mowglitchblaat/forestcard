# Site joueur et admin, en React (`apps/web`)

La réécriture du site (`index.html` de l'auteur) en TypeScript, React, Tailwind et shadcn/ui. Elle se construit **à côté** de `apps/site`, qui reste la page de l'auteur et le site publié. `apps/web` le remplace au basculement, quand toutes les vues sont portées.

Même base Supabase, mêmes fonctions SQL, même session (même clé de stockage) et mêmes ancres d'adresse (`#collection`, `#admin/cartes`) que la page de l'auteur.

## Commandes

```bash
vp dev              # depuis apps/web : serveur de développement
vp run build        # dist/
vp run test         # tests (aucun appel réseau)
```

| 3. Écriture joueur | decks (✓), dos (✓), recyclage (✓), boutique (✓), jeux du jour (✓), votes (✓), propositions (✓)                       | ✓                                 |

| 5. Basculement     | en test à `/nouveau.html` (depuis le 19 octobre 2026) ; puis `tools/pages/assemble.ts` sert `apps/web` en `/index.html` | en test                           |

Ajouts de l'amont pas encore reportés (synchro `5fabe1b`) : la vue Échanges (listée dans `NOT_YET_PORTED`, `test/views.test.ts`, le seul écart que ce test tolère), le recyclage en gold ou en fragments, la visibilité des collections limitée à celles qu'on possède, la section Échanges de « Comment jouer ». Côté admin : les réglages `vitesse_combat` et des échanges, l'éditeur de carte (`udecl` / `udx`, nouvelles conditions, programmation dans la liste des passifs). Les écritures des échanges (proposer, contribuer, annuler) passeront, dans le build de démo, par un magasin en mémoire qui applique les règles de `28-echanges.sql`, comme les propositions.

## Plus tard

- **Historique, journal stocké réduit** : la base ne garde que `c`, `t`, `txt` et `tour` de chaque ligne (voir `src/data/history.ts`). La courbe de PV, le plus gros coup, le renversement et le côté du joueur n'ont donc pas leurs données. À trancher : les relire dans le texte, ou demander à l'auteur de garder ces champs à l'enregistrement.
- **Requêtes : liste légère, détail à part** : la collection charge en une seule requête tout ce que la vue peut montrer, effets et description compris, pour chaque carte possédée (`COLLECTION_SELECT`, `src/data/cards.ts`). Optimisation possible : une liste minimale (nom, image, rareté, type, collection, ATQ / PV) et le détail d'une carte à sa sélection. À mesurer avant : le JSON des effets pèse peu à côté des images, et N requêtes de détail peuvent coûter plus qu'une seule liste complète.
- **Fraîcheur par donnée** : aujourd'hui, une règle par défaut pour toutes les requêtes (5 min, `src/main.tsx`). À régler donnée par donnée selon la façon dont elle change : les cartes du jeu (rarement), la collection (à l'ouverture d'un booster en live), l'historique (après un combat), le classement.
- **Visite guidée** (en plus de « Comment jouer ») : un parcours pas à pas de l'interface pour un nouveau joueur. Pas encore conçue.
- **La chaîne en live, partout** (point rouge dans la sidebar, « il est en live : ouvre tes boosters ») : l'état doit être dans la base. Proposition à faire à l'auteur : EventSub (`stream.online` / `stream.offline`) vers une edge function qui vérifie la signature et écrit une table `live` lisible par tous, plus une réconciliation `pg_cron` toutes les 10 minutes par Helix `GET /streams`. Le jeton Twitch du joueur ne suffit pas côté site : Supabase ne le donne qu'une fois, à la connexion, il expire en quelques heures, et le renouveler demande le secret de l'app.
- **Admin, à faire à la reprise** : les 11 sous-vues écrivent dans la base de l'auteur (cartes, effets, cadeaux, réglages) et lisent ce que seul un admin voit ; sans les droits admin, rien ne s'y teste. L'auteur les reprendra lui-même.
- **Le dos de carte sur le profil** : montrer, en grand et en mouvement (`SwayingBack`, page Dos), le dos qu'utilise le joueur. L'info est en base (`joueurs.dos_actif` → `dos_cartes.image`, le dos de base sinon : `dosDe()` de l'edge function), mais `profil_public` ne la renvoie pas, et `web` ne lit `joueurs` que pour le joueur connecté. Il faut que l'auteur ajoute `dos` (l'image résolue, ou null) à `profil_public` ; côté `web`, ce sera un champ du schéma `Profile` (`src/data/profile.ts`). Son propre dos se lirait déjà par `mes_dos()`, mais on attend que tous les profils l'aient pour le même rendu.
- **Dos de cartes hors format** : la carte est en 5:7 (`aspect-5/7` ici, `aspect-ratio: 5/7` dans l'overlay), l'image en `cover`. Trois dos sont en 2:3 (800 × 1200) et deux s'en approchent : le haut et le bas sont rognés, sur le stream comme ici. À recadrer en 5:7 côté auteur, ou à l'envoi dans l'admin.
- **Les valeurs des récompenses** : `web` lit les valeurs par défaut du moteur (`DEFAULT_RULES` de `@forestcard/engine` : victoire 50, nul 20, défaite 10), par exemple pour les repères de « Ta forme » dans l'historique. Si l'admin règle d'autres valeurs, ou si l'edge passe d'autres règles à un combat (`regles`), `web` ne le sait pas : l'historique ne stocke pas les règles d'un combat. Ça changerait si l'auteur enregistrait les règles avec chaque combat.
